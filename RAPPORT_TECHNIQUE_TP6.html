1. Introduction & Contexte du Workshop 6

Ce Workshop 6 (TP6) a pour vocation d'élever notre application Waiting Room App aux standards industriels de haute disponibilité, résilience et scalabilité. En environnement réel, une application mobile est soumise aux micro-coupures de connexion, aux latences serveur et aux variations brutales de réseau.

Le Workshop 6 introduit 7 piliers fondamentaux :

  • Surveillance fine de la connectivité réseau : distinction nette entre la connectivité physique (Wi-Fi/Cellulaire) et la disponibilité du backend Supabase.
  • Debouncing (700 ms) et contrôle de concurrence pour éliminer les clignotements d'interface lors des micro-coupures.
  • Persistance locale SQLite normalisée (waiting_queue.db) avec gestion explicite du cycle de vie via SyncStatus (pending, syncing, synced, failed).
  • Moteur de synchronisation différée automatique (SyncService) s'exécutant dès le retour du réseau, avec politique de réessai et support d'une fonction RPC PostgreSQL (register_queue_client).
  • Gestion d'état explicite via QueueState (initial, loading, loaded, empty, refreshing, loadingMore, error).
  • Pagination par lots de 20 clients avec défilement infini pour optimiser la mémoire et la bande passante.
  • Réconciliation des flux Supabase Realtime sans doublons et dans le respect strict du FIFO (First-In, First-Out).

3. Partie 1 : Modélisation des Données & Énumérations Résilientes

Étape 3.1 — Définition des Énumérations Métier (lib/models/) :

  • SyncStatus : pending (en attente), syncing (en cours), synced (synchronisé), failed (échec).
  • AppConnectivity : checking (test), online (connecté), offline (aucun réseau), backendUnavailable (serveur inaccessible).
  • QueueState : initial, loading, loaded, empty, refreshing, loadingMore, error.

Étape 3.2 — Modèle Client Immuable (lib/models/client.dart) :

class Client {
  final String id;
  final String name;
  final double? lat;
  final double? lng;
  final double? locationAccuracy;
  final DateTime createdAt;
  final SyncStatus syncStatus;

  const Client({
    required this.id,
    required this.name,
    this.lat,
    this.lng,
    this.locationAccuracy,
    required this.createdAt,
    this.syncStatus = SyncStatus.synced,
  });

  bool get hasLocation => lat != null && lng != null;
  String get locationText => hasLocation
      ? '${lat!.toStringAsFixed(4)}, ${lng!.toStringAsFixed(4)}'
      : 'Location not captured';

  Map toLocalMap() => {
    'id': id, 'name': name, 'lat': lat, 'lng': lng,
    'location_accuracy_m': locationAccuracy,
    'created_at': createdAt.toIso8601String(),
    'sync_status': syncStatus.name,
  };

  Map toSupabaseMap() => {
    'id': id, 'name': name, 'lat': lat, 'lng': lng,
    'location_accuracy_m': locationAccuracy,
    'created_at': createdAt.toIso8601String(),
  };
}

4. Partie 2 : Surveillance Réseau Avancée & Debouncing

Étape 4.1 — ConnectivityService (lib/services/connectivity_service.dart) :

Ce service combine l'écoute des interfaces matérielles avec un ping léger sur la table Supabase (timeout de 5 secondes) pour confirmer la joignabilité effective de la base de données distante.

Étape 4.2 — ConnectivityProvider avec Debouncing (lib/providers/connectivity_provider.dart) :

Lors d'un changement de statut réseau, un timer de 700 ms est déclenché. Si le réseau est stable, la vérification du backend Supabase s'exécute avec gestion d'une file d'attente concurrente (_checkAgain) et nettoyage strict lors du dispose().

Étape 4.3 — Bandeau Contextuel Réactif (lib/widgets/offline_banner.dart) :

Affiche instantanément un bandeau d'alerte en haut d'écran : rouge (No network connection), orange (Waiting-room server unavailable) ou bleu (Checking connection...).

5. Partie 3 : Persistance SQLite & Moteur de Synchronisation Automatique

Étape 5.1 — LocalQueueStorage (lib/storage/local_queue_storage.dart) :

Crée et gère la base locale waiting_queue.db avec la table clients. La méthode getPendingClients() sélectionne les enregistrements pending et failed ordonnés par created_at ASC pour respecter scrupuleusement l'ordre d'arrivée FIFO lors de la synchronisation.

Étape 5.2 — SyncService (lib/services/sync_service.dart) :

Orchestre la transmission sécurisée vers Supabase. Chaque client passe successivement par le statut syncing, puis synced (en cas de succès) ou failed (pour réessai ultérieur) :

Future synchronize() async {
  if (_isSyncing) return;
  _isSyncing = true;
  try {
    final pending = await _storage.getPendingClients();
    for (final record in pending) {
      final id = record['id'] as String;
      try {
        await _storage.updateSyncStatus(id, SyncStatus.syncing);
        await _repository.registerOnServer(Client.fromLocalMap(record));
        await _storage.updateSyncStatus(id, SyncStatus.synced);
      } catch (_) {
        await _storage.updateSyncStatus(id, SyncStatus.failed);
      }
    }
  } finally {
    _isSyncing = false;
  }
}

Étape 5.3 — Fonction Stockée PostgreSQL RPC & Repli Résilient (lib/repositories/queue_repository.dart) :

Le dépôt distant invoque la procédure stockée PostgreSQL register_queue_client. Pour pallier toute indisponibilité de la procédure ou absence de colonnes optionnelles, un mécanisme de repli à 3 niveaux a été implémenté : appel RPC ➔ upsert complet ➔ upsert sans location_accuracy_m ➔ upsert minimal.

6. Partie 4 : Gestion d'État Avancée, Pagination & Realtime

Étape 6.1 — Pagination Paginée par Lots de 20 (lib/providers/queue_provider.dart) :

La file d'attente est initialisée avec les 20 premiers enregistrements via fetchInitialQueue(). L'écoute du défilement (ScrollController) déclenche loadMore() dès que l'utilisateur approche du bas de la liste (seuil de 200 px) :

Future loadMore() async {
  if (_isLoadingMore || !_hasMore) return;
  _isLoadingMore = true;
  notifyListeners();
  try {
    _page++;
    final newClients = await _repository.fetchPage(
      offset: _page * _pageSize, limit: _pageSize,
    );
    final existingIds = _clients.map((c) => c.id).toSet();
    _clients.addAll(newClients.where((c) => !existingIds.contains(c.id)));
    if (newClients.length < _pageSize) _hasMore = false;
  } catch (_) { _page--; }
  finally { _isLoadingMore = false; notifyListeners(); }
}

Étape 6.2 — Réconciliation Realtime Anti-Doublon & FIFO :

À chaque réception d'un événement d'insertion temps réel, l'identifiant est vérifié pour éviter les doublons avec les créations locales optimistes, et la liste est instantanément ordonnée selon la date de création createdAt.
